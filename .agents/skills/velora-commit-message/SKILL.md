# 提交信息规范

三段结构：

```
类型(范围): 简短描述          ← 标题：一句话说清这次变更
                              ← 空行
背景 / 实现 / 影响 / 测试      ← 正文：为什么改、怎么改、影响、验证
                              ← 空行
BREAKING CHANGE / Closes …    ← 脚注：破坏性变更、关联 issue、协作者
```

## 1 标题写什么

标题是 commit 的门面，一句话说清楚这次变更。

```
feat(auth): 支持 OAuth2 登录
fix(order): 修复优惠券重复抵扣
refactor(api): 提取统一响应处理
docs(readme): 补充本地开发说明
```

要求：

- **简短**：理想 ≤ 50 字符，最多 72。太长说明细节该进正文。
- **动词开头、祈使句**：英文用 add / fix / update / remove / refactor，不用 added / fixes；中文用 新增 / 修复 / 优化 / 移除 / 重构 / 调整 / 更新。
- **不要句号结尾**：`fix(auth): 修复 token 刷新失败。` ❌ → `fix(auth): 修复 token 刷新失败` ✅
- **不要空话**：`fix bug`、`update code`、`修改`、`提交`、`WIP` ❌；要写成 `fix(auth): 修复 token 过期后未自动刷新导致 401`。
- **type 与 scope 要准确**：type 是变更类别，scope 可选、指模块（auth / api / ui / order / deps）。
- **破坏性变更**用 `!` 标出：`feat(api)!: 移除 v1 用户接口`。

## 2 正文写什么

正文不是重复 diff，而是解释 diff 看不出来的信息。小改动标题可能就够；复杂改动正文很重要。正文回答：

- **为什么改**：背景、需求、bug 症状、业务原因。例：旧逻辑在并发下会重复扣库存。
- **改了什么**：高层次描述，不逐行解释代码。例：新增库存锁服务，扣减前先获取分布式锁。
- **怎么实现的**：关键方案、设计决策、权衡。例：选 Redis 锁而不是数据库行锁，因为扣减频率高。
- **有什么影响**：是否破坏兼容、是否要数据库迁移 / 配置变更 / 重新部署、API 与数据格式与依赖版本是否变化、有没有副作用与后续计划。
- **如何验证**：新增了哪些测试、手动验证了哪些流程、有没有性能数据、有没有后续计划。例：当前只支持单仓拆单，多仓拆单后续迭代。

格式：每行尽量 ≤ 72 字符，便于终端阅读；用列表：

```
背景：
- …

实现：
- …

影响：
- …

测试：
- …
```

### 写作口径：专业、中性、可核对

提交信息是给同事、代码审查者与未来的自己读的正式文本，不是现场记录。

- **写客观事实与机制，不写叙事口吻**：不要“用户报修”“用户反馈”“我发现”“终于修好了”这类话，也不要情绪、趣语与表情。
- **现象写成可复现的描述**，带上前提：
  - ✅ `两行列表项全选后按删除，缓冲区残留 ** 与 。`
  - ❌ `用户报修删完还剩东西`
- **根因写到具体的层与量**：
  - ✅ `端点是拖动当刻的显示偏移；块首记号随光标显形后同一块由 203 字节变 207，末端 4 字节既未高亮也未删除`
  - ❌ `我以为是缓存问题，结果是在另一个地方算错了`
- **不归因于人**：不写谁引入的，不点名；用现在时或简单过去时。
- **可核对**：引文件用 `路径:函数名`；数字当场实测（通过数、耗时、字节数、尺寸），并写清未验证的边界。

## 3 脚注写什么

脚注放关联信息、破坏性变更、协作者。

```
BREAKING CHANGE: 描述不兼容变更和迁移方式
Closes #123           合并后自动关闭
Fixes #123            表示修复了某个 issue
Refs #123             仅引用，不自动关闭
Co-authored-by: Name <email>     多人协作提交
Signed-off-by: Name <email>      DCO 签名
```

破坏性变更必须显著标出：标题里的 `!` 表示有破坏性变更，脚注里的 `BREAKING CHANGE:` 进一步说明迁移方式。

```
feat(api)!: 移除 v1 用户接口

BREAKING CHANGE: /api/v1/users 已移除，请迁移到 /api/v2/users。
```

## 4 类型表与它的好处

| 类型 | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `docs` | 文档变更 |
| `style` | 格式调整，不影响逻辑 |
| `refactor` | 重构，不是新功能也不是修复 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建系统或依赖变更 |
| `ci` | CI 配置变更 |
| `chore` | 杂项，不修改 src/test |
| `revert` | 回滚提交 |

好处：可自动生成 changelog；可配合 semantic-release 自动决定版本号（`feat` 升 minor，`fix` 升 patch，`BREAKING CHANGE` 升 major）；便于团队统一审查和检索。

## 5 完整例子

```
feat(checkout): 支持优惠券与积分叠加使用

背景：
- 运营需要在大促期间允许用户同时使用优惠券和积分。
- 旧逻辑检测到优惠券后直接跳过积分抵扣。

实现：
- 将价格计算拆为 coupon、points、shipping 三个独立步骤。
- 新增 PriceCalculator，保留旧接口兼容。
- 增加配置项 checkout.stack_discounts，默认关闭。

影响：
- 数据库无变更。
- 管理后台需开启新配置后生效。
- API 响应新增 discount_details 字段，向后兼容。

测试：
- 新增单元测试覆盖叠加、互斥、最低价保护。
- 手动验证下单、支付、退款、对账流程。

Closes #456
```

## 6 不同场景的写法重点

### Bug 修复

重点写：症状（什么条件下出现）、根因（旧代码为什么错）、修复（怎么改）、回归（加了什么测试）。

```
fix(order): 修复并发下单导致库存超卖

根因：
- 扣减库存前未加锁，两个请求同时读到相同库存。

修复：
- 使用 Redis 分布式锁按商品维度串行扣减。
- 扣减失败时回滚订单状态。

测试：
- 新增并发测试，模拟 100 个请求同时下单。
```

### 重构

重点写：行为不变、为什么重构、范围是什么。

```
refactor(api): 提取统一响应处理

行为不变。
将各 controller 中重复的 success/error 包装逻辑提取到 ResponseHelper。
```

### 性能优化

重点写：优化前后数据、优化手段、是否影响功能。

```
perf(search): 优化商品搜索接口响应时间

将模糊查询改为 Elasticsearch 前缀查询。
压测 QPS 从 120 提升到 450，P99 从 800ms 降到 120ms。
```

### 依赖升级

重点写：升级了什么版本、为什么升级、是否有破坏性变更、是否需要迁移。

```
build(deps): 升级 Spring Boot 2.7 到 3.2

原因：
- 2.7 已停止维护。
- 需要 Jakarta EE 支持。

影响：
- javax.* 迁移到 jakarta.*。
- 需重新验证数据库驱动和 Spring Security 配置。
```

### 回滚

重点写：回滚哪个提交、为什么回滚、后续计划。

```
revert: feat(order): 支持按商品拆单

原因：
- 拆单后支付回调状态不一致，导致部分订单无法发货。
- 先回滚，修复后再重新提交。

Refs #789
```

## 7 提交前检查清单

- [ ] 标题是否简短、明确、动词开头？
- [ ] 类型和 scope 是否准确？
- [ ] 标题是否没有句号、没有空话？
- [ ] 正文是否保持专业中性（无“用户报修”类叙事、无情绪、不归因于人）？
- [ ] 正文是否说明了"为什么"？
- [ ] 是否说明了关键实现和设计决策？
- [ ] 是否说明了影响、兼容性、迁移步骤？
- [ ] 是否说明了如何测试？（代码类改动写出实测命令与结果）
- [ ] 破坏性变更是否用 `!` 和 `BREAKING CHANGE:` 标出？
- [ ] 是否关联了 issue？
- [ ] 是否一个 commit 只做一件逻辑上的事？
- [ ] 语言是否统一？中文还是英文，团队要一致。
- [ ] 是否包含敏感信息？commit message 可能被公开。
